# 바른 API 연결 순서

## 1. 사용자가 바른에서 준비할 것

1. https://bareun.ai/ 에 가입하고 이메일 인증을 완료합니다.
2. Free 플랜인지 확인합니다. 카드가 필요한 Standard 1개월 체험과 구분합니다.
3. 내 정보/API 키 화면에서 키를 발급받습니다.
4. 키는 채팅, GitHub, `supabase-config.js`에 붙여 넣지 않습니다.

공식 요금표는 Free 월 50,000어절, 일반 `CorrectError` 사용을 안내합니다.
정책은 변경될 수 있으므로 계정의 실제 권한과 사용량 화면을 확인해야 합니다.
공식 문서에 따르면 스트리밍 교정은 Free에서 사용할 수 없어 이 프로그램도 사용하지 않습니다.
- https://bareun.ai/product
- https://bareun.ai/product/billing-guide
- https://bareun.ai/docs/howtouse/api-correct/

## 2. Supabase 호출 제한 설정

SQL Editor → New query에 `supabase/bareun-quota.sql` 전체를 붙여 넣고 Run을 누릅니다.
검사 기록 테이블은 변경하지 않습니다. 원문과 API 키도 이 테이블에 저장하지 않습니다.
요청 ID·사용자 ID·시각·호출 수·글자 수만 기록합니다.

실행 전에는 외부 호출을 차단하고 기본 규칙 검사만 수행합니다.
브라우저나 Vercel 함수 메모리만으로 제한하면 동시 실행·재시작 때 우회될 수 있어
DB 함수가 월별 행을 잠그고 한도를 먼저 예약합니다.

초기 한도(이 프로젝트에서 정한 값이며 바른의 공식 제한과 다릅니다):
- 한 검사: 짧은 문단을 묶고 긴 문단을 나누어 묶음당 최대 1,000 UTF-16 단위, 최대 10묶음·1만 단위
- 규칙 검사는 전체 추출 텍스트에 적용합니다. 오류를 발견한 문단도 외부 검사 대상에 포함합니다.
- 문단 사이에는 줄바꿈을 넣고 원문 위치 대응표를 보관합니다. 분할 경계의 문맥은 확인 필요로 남깁니다.
- 사용자: 외부 검사 요청 간격 1분, 하루 바른 호출 20회
- 사이트 전체: 하루 바른 호출 20회, 월 100회, 월 전송 길이 20,000단위
- 하루·월 경계: UTC (한국에서는 오전 9시 경계)
- 예약 뒤 실패하거나 사용자가 취소해도 반환하지 않습니다. 자동 재시도하지 않습니다.
- 같은 탭에서 최근 100개 묶음의 성공 응답을 재사용합니다. 변경되지 않은 묶음과 한 요청 안의 같은 묶음도 중복 호출하지 않습니다. 새로고침하면 캐시는 초기화됩니다.

이전 SQL을 실행했다면 수정된 `bareun-quota.sql` 전체를 다시 실행해야 합니다.
기존 검사 기록·사용량·요청 이력을 삭제하거나 초기화하지 않고 함수의 허용 범위만 바꿉니다.
기존 설정 그대로면 3회보다 큰 요청이 거부되며 기본 검사는 계속 동작합니다.
월 100회·2만 자와 사이트 전체 일 20회 제한은 늘리지 않았습니다.

월 2만 자 제한은 비용 소모를 줄이는 보수적인 자체 제한이며 바른의 어절 차감 계산과 같지 않습니다.
같은 키를 다른 앱에서 사용한 양은 이 DB가 알 수 없습니다. 바른 사용량도 함께 확인하세요.
익명 인증은 브라우저 데이터 삭제로 바뀔 수 있습니다. 그래도 사이트 전체 한도는 유지됩니다.
키 공유·직접 호출은 이 한도의 보호 밖입니다. 키는 Vercel 서버 환경에만 둡니다.

## 3. Vercel 환경 변수 입력 (사용자가 직접)

프로젝트 Settings → Environment Variables에서 Production에 다음을 추가합니다.
Preview에서도 쓸 경우 Preview에 같은 설정을 넣되 사용량은 공유됩니다.

| 이름 | 값 |
|---|---|
| BAREUN_API_KEY | 바른에서 발급받은 비밀 키 |
| SUPABASE_URL | 현재 프로젝트의 https://...supabase.co 주소 |
| SUPABASE_PUBLISHABLE_KEY | 현재 사용하는 sb_publishable_... 공개 키 |
| BAREUN_ALLOWED_ORIGIN | https://document-error-checker-frontend.vercel.app (끝에 / 없이) |

Supabase service_role/secret 키는 필요하지 않습니다.
바른 키는 서버 환경 변수로만 읽습니다. 프론트엔드에는 키를 전달하지 않습니다.
환경 변수를 바꾸면 Vercel에서 새 배포가 필요합니다.

## 4. 코드 배포와 확인

GitHub Desktop Commit → Push → Vercel 최신 커밋 Ready/Production 확인 → 강력 새로고침.
Root Directory `frontend`, Other, 기존 빌드/출력 설정을 유지합니다.
`frontend/api/proofread.js`가 Vercel 함수가 되어 `/api/proofread`로 실행됩니다.
기존 순수 정적 HTTP 서버에는 이 함수가 없어 외부 검사만 실패합니다. 기본 검사는 계속 됩니다.
서버 환경 변수와 SQL이 준비된 뒤 실제 배포 환경에서 확인해야 합니다.

맞춤법 항목에서 '바른 API 외부 검사도 사용하기'에 동의하고 검사합니다.
파일·파일명 대신 선택한 문단 텍스트만 우리 서버를 거쳐 바른으로 전송합니다.
원문 위치가 일치하지 않는 수정, 확인 필요 범주, 추출이 불확실한 내용은 검사 불가입니다.
API 후보가 없더라도 완전한 정상이라고 확정하지 않습니다. 자동으로 파일을 고치지 않습니다.
기본 규칙 결과와 외부 후보를 합쳐 기존 결과 JSON·Supabase 기록에 저장합니다.
이전 기록은 저장 당시의 결과이며 조회할 때 외부 검사를 다시 호출하지 않습니다.

## 5. 테스트

```powershell
node tests/bareun-server.cjs
node tests/bareun-client.cjs
node tests/history.cjs
```

위 테스트는 모의 응답을 사용하며 실제 바른 키·무료 사용량은 소모하지 않습니다.
DB 함수의 실제 동시 실행과 무료 키 권한은 SQL 실행·배포 후 별도로 검증해야 합니다.

실제 연결 테스트는 정상 문장/오류 문장 2개를 보내 바른 호출 2회를 소비하고 익명 사용자를 만듭니다.
바른 키를 로컬에 입력할 필요 없이 서버 환경 변수만 사용합니다.

```powershell
$env:BAREUN_TEST_SITE='https://document-error-checker-frontend.vercel.app'
node tests/bareun-live.cjs
```

설정하지 않으면 SKIP으로 끝납니다. SKIP은 연결 성공이 아닙니다.
실패 시 제공사 오류 원문이나 키를 출력하지 않습니다. 바른 대시보드의 키 권한·한도를 확인하세요.

## 남은 한계

- 실제 API 키가 준비되기 전에는 실서비스 교정 품질을 검증할 수 없습니다.
- 한 번에 최대 1만 자이며 남은 예산이 부족하면 전체 외부 요청이 거부될 수 있습니다. 부분 예산에 맞춘 자동 재요청은 하지 않습니다.
- 결과와 과거 기록에 API 응답 수신 글자 수·미검사 글자 수와 원문 구간별 범위를 저장합니다.
- API 응답 수신은 수정 위치까지 모두 해석했거나 문장 전체가 정상이라는 뜻이 아닙니다.
- 문단/묶음 사이의 문맥과 PDF 줄바꿈은 한계입니다. 긴 문단의 분할 후보는 확인 필요로 표시합니다.
- API 위치 길이가 없거나 0인 경우 원문 내용과 시작 위치가 일치할 때만 길이를 추론합니다.
- 공백 삭제 전용 범위와 중첩 블록의 개별 반영은 지원하지 않고 검사 불가 안내를 남깁니다.
- 제한 테이블은 사용 이력으로 조금씩 증가합니다. 운영이 길어지면 과거 기간 정리 작업이 필요합니다.
- 공개 서비스의 익명 사용자 생성·호출 남용을 완전히 차단하지는 않습니다. 전체 한도로 키 사용량을 제한합니다.
